# AIWebNovel Codex全局开发说明 v1.0

## 1. 项目目标

开发一套面向中文男频网文作者、运行于Windows 11本地环境、由Codex提供在线创作与语义评审能力的多Agent长篇小说创作系统。

第一版验证方向：

- 简体中文；
- 男频都市异能；
- 番茄男频节奏；
- 单个正文生成单元500～1000字；
- 单章约2000～3000字；
- 10万字为MVP验证节点；
- 系统必须继续支持约100万字长篇及全书完结。

该产品不是单Prompt续写工具，也不是自动批量生成小说的聊天界面。

核心价值：

1. 剧情由人物、利益、认知、环境和因果自然推动；
2. 一个主写作Agent、多位独立评审Agent、一个总编Agent；
3. 正文生成、独立评审、返修、作者确认和正式事实提交形成闭环；
4. 长期追踪人物状态、关系、认知、物品、事件和伏笔；
5. 正式数据、候选数据和分支数据严格隔离；
6. AI味控制从第一段正文开始参与；
7. 作者修改可形成可解释、可撤销、版本化的项目风格经验；
8. 所有复杂任务必须拆分为小任务；
9. 所有用户可见功能必须具备真实后端行为；
10. 模型不得直接修改正式故事事实。

## 2. 技术栈

后端：

- Python 3.12.10
- FastAPI
- Uvicorn
- Pydantic
- SQLAlchemy 2.x
- Alembic
- SQLite，启用WAL和外键

前端：

- React
- TypeScript
- Vite

架构：

- Windows 11本地优先
- 模块化单体
- 本地浏览器界面
- 后端只绑定127.0.0.1
- 用户数据位于 `%LOCALAPPDATA%\AIWebNovel`
- 不使用微服务
- 不使用Redis
- 不使用Celery
- 第一版不依赖Docker或WSL

Codex：

- 通过统一`CodexExecutor`适配器接入
- 优先官方Python SDK适配器
- 保留`codex exec`后备适配器
- 业务代码不得直接依赖具体SDK或CLI
- ChatGPT认证由Codex官方机制管理
- 应用不得保存密码、Cookie或明文令牌

## 3. 四层能力架构

系统能力分为：

1. 用户可见岗位；
2. 工作流；
3. 36个内部原子Skill；
4. 确定性代码服务。

不能把岗位、工作流、Skill和代码服务混为同一概念。

用户界面默认显示通俗岗位名称，不直接暴露Skill ID。专业模式可以查看Skill、Prompt和任务详情。

## 4. 模块边界

业务模块：

- Project
- Market
- StoryBible
- Planning
- Writing
- Review
- Canon
- Style
- Analytics
- Workflow

基础设施模块：

- Assets
- Search
- CodexRuntime
- Infrastructure

每类数据只有一个权威所有者。

明确禁止：

- Writing直接写Canon表；
- Review直接修改正文；
- Planning直接修改正式状态或事实；
- Style直接修改正文；
- Market或Analytics自动改变正式项目；
- CodexRuntime访问业务数据库Repository；
- Search成为正式事实来源；
- 前端直接访问SQLite；
- Workflow绕过应用服务直接写业务表。

跨模块只能使用公开应用服务、版本化DTO和持久化领域事件。

## 5. 数据与版本原则

所有主要业务对象使用带类型前缀的ULID。

重要对象采用：

- 稳定身份对象；
- 不可变版本对象；
- 当前版本指针。

禁止覆盖历史版本。

关键写请求必须提供：

- project_id
- branch_id
- expected_revision_id
- reason
- request_id或Idempotency-Key

版本不匹配时必须返回冲突，不能覆盖新内容。

系统操作时间保存UTC；故事内部时间使用独立字段。

## 6. 三个数据区域

必须严格区分：

- 正式区；
- 候选区；
- 分支区。

候选正文、候选规划、候选事实和候选风格规则不得自动进入正式区。

分支数据不得自动进入正式主线。

正式变更必须由作者明确确认。

## 7. 作者确认原则

作者确认必须绑定：

- 对象；
- 精确版本ID；
- 内容哈希；
- 分支；
- 确认类型；
- 时间。

作者修改内容后，原确认立即失效。

模型声称“用户已经同意”不构成作者确认。

正文确认与正式事实提交是两个独立步骤：

1. 确认正文版本；
2. 审查并提交正式事实。

## 8. Canon权限

采用P0—P4权限模型。

- P0：读取当前用户输入；
- P1：读取当前任务所需正式数据；
- P2：写入候选区；
- P3：提出正式变更；
- P4：执行确定性正式提交。

任何模型、Agent或Prompt都不能获得P4。

`canon.commit`必须是确定性本地代码服务。

一次正式提交必须原子更新：

- 正式正文指针；
- 事件；
- 事实；
- 人物状态；
- 关系；
- 物品和资源；
- 角色认知；
- 伏笔；
- 快照；
- 审计记录；
- 检查点。

任一部分失败，整次事务回滚。

## 9. 创作单位与确认方式

默认正文生成单位：

- 500～1000个中文字符。

默认章节长度：

- 2000～3000个中文字符。

默认确认模式：

- 每个正文单元完成强制评审后等待作者确认。

支持“本章连续候选模式”，但：

- 默认关闭；
- 后续场景只能引用本章临时候选；
- 不得提交正式事实；
- 不得自动开始下一章；
- 前文修改后必须分析对后续候选的影响；
- 必须设置明确停止点。

## 10. 多Agent质量闭环

第一条纵向闭环必须包括：

- 剧情就绪检查；
- 场景诊断；
- 动作链；
- 正文生成；
- 写作端自检；
- 人物因果独立评审；
- 连贯与角色认知独立评审；
- 语言叙事与AI味独立评审；
- 总编裁决；
- 必要时定向返修；
- 独立返修复核；
- 作者确认；
- 候选事件和状态提取；
- 候选认知变化提取；
- 候选伏笔变化提取；
- 正式变更预览；
- 确定性正式提交。

独立评审在提交前不得查看其他评审的意见。

总编不得使用简单多数票或平均分替代裁决。

返修Agent不得自行验证返修成功。

## 11. 硬错误和软问题

硬错误默认允许有限自动返修，包括：

- 正式事实冲突；
- 角色认知越权；
- 时间、地点、物品或伤势冲突；
- 使用尚未获得的能力或资源；
- 破坏锁定内容；
- 错误分支；
- 严重因果断裂；
- 强行推进尚未就绪剧情。

软问题默认等待作者决定，包括：

- 幽默强弱；
- 节奏偏好；
- 情绪表达；
- AI味审美判断；
- 句段风格；
- 是否删除某段。

作者可对当前场景或章节临时授权软问题自动返修，但授权不得自动延续到全项目。

最多自动返修三轮。三轮失败后停止并等待作者。

不得通过降低质量阈值继续。

## 12. AI味控制

AI味控制是第一版核心功能，不是后续扩展。

必须组合：

1. 确定性语言和结构统计；
2. 本地中文AI文本检测器；
3. 项目作者偏好匹配；
4. 独立语言叙事评审；
5. 多章节趋势分析。

本地检测器仅提供辅助信号，没有独立否决权。

系统目标是提高：

- 自然度；
- 人物感；
- 叙事适配；
- 内容与句段形式匹配。

不得以规避检测器为目标。

禁止通过以下方式降低检测分数：

- 故意添加错字或病句；
- 随机切碎句子；
- 添加无意义动作；
- 机械替换同义词；
- 随机改变段落长度；
- 使用口语词堆积。

原则：

“形式由内容、人物状态和叙事功能决定。”

AI味评审必须提供精确证据，不能只输出模糊总分。

## 13. 长篇记忆

必须支持：

- 人物档案；
- 人物状态；
- 单向关系；
- 能力定义和状态；
- 物品与资源；
- 地点；
- 事件；
- 正式事实；
- 命题；
- 角色认知；
- 错误信念；
- 信息传播；
- 推理链；
- 伏笔；
- 读者认知；
- 来源证据和历史版本。

数据库是唯一事实来源。

全文搜索和向量检索只用于召回，不能证明事实成立。

模型上下文是只读、不可变快照。

## 14. 上下文规则

不得把小说全文发送给模型。

每次只提供完成当前任务所需的最小上下文。

强制上下文包括：

- 当前任务；
- 当前场景；
- 相关人物状态；
- 相关人物认知；
- 当前禁止事项；
- 上一正文单元结尾。

超过预算时：

1. 保留强制上下文；
2. 保留直接相关内容；
3. 使用已确认摘要；
4. 拆分任务；
5. 记录省略内容及原因。

禁止静默截断。

## 15. Codex沙箱

创作模式中的每次Codex调用必须使用独立任务沙箱。

Codex只能：

- 读取当前任务的只读输入；
- 写入受限输出目录。

Codex不得：

- 读取SQLite数据库文件；
- 读取其他项目；
- 读取备份；
- 读取应用源码；
- 修改Git仓库；
- 修改Prompt源文件；
- 修改数据库迁移；
- 安装依赖；
- 执行任意PowerShell；
- 访问系统凭据；
- 写入沙箱外部。

输出至少采用：

- result.json
- prose.md

所有输出进入候选区前必须经过：

- Schema验证；
- 权限验证；
- 文件类型和大小验证；
- 截断检查；
- 版本检查；
- 分支检查；
- 内容完整性检查。

## 16. 开发与创作隔离

开发模式只能使用：

- 开发数据库；
- 测试数据库；
- 示例项目；
- 测试资产。

不得访问作者正式创作项目和正式备份。

创作模式不得修改应用代码。

## 17. UI真实性

所有用户可见功能必须具备：

- 前端组件；
- API；
- 参数验证；
- 权限检查；
- 业务逻辑；
- 数据持久化；
- 状态刷新；
- 用户反馈；
- 自动测试。

每项功能登记唯一feature_id。

以下情况禁止进入稳定版本：

- 空按钮；
- 固定假数据；
- 假进度条；
- 不持久化的开关；
- 成功提示但数据库未改变；
- 没有后端行为的统计；
- 未实现却显示为稳定功能；
- 用FakeExecutor冒充真实创作。

## 18. 工作流和任务

所有复杂操作通过持久化工作流执行。

任务状态必须真实保存，并支持：

- 排队；
- 依赖；
- 运行；
- 输出验证；
- 成功；
- 阻塞；
- 等待作者；
- 可恢复失败；
- 永久失败；
- 取消；
- 过期。

同一时间最多运行一个Codex任务。

网络、登录或额度恢复后不得自动重新运行任务，必须由作者确认。

任务进度来自真实节点状态，不得制造虚假百分比。

## 19. 离线行为

离线时仍允许：

- 查看和编辑；
- 版本管理；
- 搜索；
- 本地统计；
- 已安装的本地AI检测；
- 导入导出；
- 备份恢复；
- 手动审查已有候选事实。

暂停：

- Codex正文生成；
- Codex语义评审；
- 模型事实提取；
- 模型风格规则建议。

不得用本地检测器冒充Codex语义评审。

## 20. 能力包

核心引擎、题材包、平台包、项目规则和作者规则必须分层。

第一版内置：

- genre.urban_supernatural
- platform.fanqie_male

项目绑定精确能力包版本。

更新应用或能力包后不得自动改变旧项目行为。

能力包和Prompt升级必须：

- 创建新版本；
- 运行测试；
- 比较差异；
- 由作者确认。

题材包和平台包默认不得携带或执行代码。

Agent不得自行修改Prompt、创建Skill、安装依赖或升级能力包。

## 21. 测试和完成定义

任何开发任务要标记完成，必须根据适用范围包含：

- 实现代码；
- 数据迁移；
- API；
- UI；
- 权限；
- 状态迁移；
- 自动测试；
- 失败路径；
- 文档；
- 功能真实性矩阵更新。

不适用项必须明确说明原因。

不得以以下证据宣布完成：

- 页面可打开；
- 接口返回200；
- 截图看起来正确；
- 留有TODO；
- 使用模拟数据；
- 测试未运行；
- 测试被跳过；
- 只进行一次人工演示。

核心测试失败时不得继续下一任务。

## 22. 开发顺序

唯一开发阶段为0—12：

0. 工程底座；
1. 项目、版本与三区隔离；
2. 故事世界、认知和正式事实模型；
3. 工作流和持久任务；
4. Codex适配器、上下文和沙箱；
5. 首个多Agent场景闭环；
6. 完整章节与正式事实提交；
7. 作者风格学习；
8. 长篇规划与四章循环；
9. 市场、选题与赛马；
10. 平台数据导入与复盘；
11. 安装、备份与灾难恢复；
12. 10万字长程验证。

不得以实现方便为理由跳过或重排关键依赖。

## 23. 明确排除

第一版不实现：

- 云端用户账号；
- 多人协作；
- 完整移动端应用；
- 本地大型写作模型；
- 平台自动发布；
- 自动网页抓榜；
- 未经审查的插件市场；
- 多个主写作Agent竞争正文；
- 无限自动生成；
- 自动降低质量门槛；
- 以规避AI检测器为目标的改写；
- 微服务；
- Redis；
- Celery；
- Docker强依赖。

## 24. 工作纪律

执行任务时：

1. 先阅读本文件和当前任务包；
2. 检查依赖任务是否完成；
3. 只修改允许目录；
4. 不实现任务之外的业务能力；
5. 不删除或弱化已有测试；
6. 遇到规格冲突时停止并报告；
7. 发现无法完成的部分时明确列出，不伪造完成；
8. 完成后运行任务要求的全部测试；
9. 输出改动摘要、测试结果、已知限制和后续依赖；
10. 未通过完成定义时，状态必须为未完成。
